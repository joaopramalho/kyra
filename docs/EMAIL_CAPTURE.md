# Website lead capture

The anonymous capture endpoint and the dependency-free `lmc-form.js` loader are implemented. The email consumer is now connected to the worker when enabled; see [EMAIL_RUNTIME](EMAIL_RUNTIME.md) for its startup flag and provider configuration. The full hosted deployment remains unfinished. The integration test below exercises the actual queue worker with fake external providers.

## Install the form

1. Configure the business's canonical services, staff, hours and calendar. Email availability uses those records; the new email settings screen does not yet include a business-hours editor.
2. Open **Email automation** (`/settings/email`). Select services, service-area ZIPs, the owner address, a physical footer address and approved emergency text. Configure permitted actions and follow-ups, save and enable email processing.
3. Copy the **Website form snippet** shown when the capture token is created. Paste it into the website's HTML where the form should appear. For an existing configuration whose token was not saved, replace the capture token and update every existing form using it.

```html
<script
  src="https://YOUR_LMC_ORIGIN/lmc-form.js"
  data-capture-token="YOUR_CAPTURE_TOKEN"
  defer
></script>
```

Use the actual origin and token generated by the dashboard. HTTPS is required outside local development. The form renders at the script location; scripts in the document head render at the end of the body after it becomes available. Multiple script elements can create independent forms.

Capture tokens are public intake capabilities. They cannot read lead history, authorize a reply or verify a booking requester. The server checks the stored token hash, enabled configuration, request size, schema, suppression and sender/tenant limits. Replacing the token invalidates previous forms immediately. The operator UI requires acknowledgment before replacement.

## Behavior and privacy

The form asks for an optional name, an email address and a message. Follow-up consent is an explicit, initially unchecked checkbox. No phone, attachments, cookies, browser storage or tracking are required. It sends JSON using `credentials: "omit"` and `referrerPolicy: "no-referrer"` to the loader's origin. The endpoint permits anonymous CORS; operator APIs remain authenticated and CSRF protected.

Each submitted payload has a random UUID. A retry after a timeout or lost acknowledgment reuses the same UUID and payload; a changed payload gets a new UUID. A successful request clears the form and consent. No automatic retries run in the visitor's browser. The form reports request acceptance, not email delivery or booking. Email bookings still require a verified conversation reply.

All markup is constructed with DOM APIs and fixed text. Visitor content and API errors are never inserted as HTML. Inline styles are isolated in an open shadow root. A script `nonce` is propagated to the form's style element when the embedding site's CSP requires a style nonce. The site must allow the LMC origin in its `script-src` and `connect-src` policies; its own CSP continues to apply.

Optional host CSS properties: `--lmc-form-foreground`, `--lmc-form-background`, `--lmc-form-border`, `--lmc-form-button`, and `--lmc-form-button-text`. Default colors use browser system colors and a neutral border; the form inherits the host font.

## Verification

```sh
pnpm --filter @lobbystack/admin exec vitest run \
  src/lib/lmc-form.test.ts src/lib/lmc-form-snippet.test.ts \
  src/components/live-lmc-settings-surface.test.tsx
```

For the database integration test, provide an isolated local test database with the applied schema and explicit runtime-role URLs: `LMC_TEST_DATABASE_URL`, `LOBBYSTACK_APP_DATABASE_URL`, `LOBBYSTACK_WORKER_DATABASE_URL`, and `LOBBYSTACK_DISPATCHER_DATABASE_URL`. The helper refuses production, remote databases, databases without `test` in their name and runtime roles targeting a different database. No privileged fallback is used for application actions.

```sh
LMC_FORM_INTEGRATION_TEST=1 pnpm --filter @lobbystack/admin exec vitest run \
  --config vitest.lmc-form.config.mts
```

This test runs the actual browser form code in jsdom, posts to the production capture HTTP handler, persists through PostgreSQL and processes the real queued email worker. A deliberately lost acknowledgment after server acceptance is retried; the test requires exactly one stored lead and one outgoing fake-provider response. It does not contact real email, calendar or model providers. Browser preview separately verifies cross-origin delivery to the local API and the unavailable-form message for an invalid token.
