# Configured pilot dashboard pages

Pilot tenants configured by CLI do not use the inherited voice/billing onboarding flow. Their dashboard entry is nevertheless closed unless the **actual session user** is verified in the Auth database, has a canonical active business, has an active recognized membership in that business (at least viewer), and that business has a valid native LMC configuration. Missing/invalid state returns 404, except a **verified, signed-in account with no active business** is redirected from the dashboard to a guarded `/setup-required` page describing the operator-controlled tenant bootstrap. The setup page does not create a business or grant CRM access; unverified, foreign, revoked, or misconfigured memberships remain denied. Tenant/user/system headers do not select the operator or grant access. Email verification is read only through the Auth role; App grants were not widened.

`resolveLmcPilotPageAccess` checks these conditions through the dedicated Auth/App clients and scoped transaction. A paused automation configuration remains eligible so its operator can manage settings. Existing API roles still govern reads, replies, settings writes and scheduling; a viewer does not acquire write privileges from page access. No legacy onboarding stage is advanced or rewritten. With pilot mode off, the original complete-onboarding requirement and navigation remain intact. The pilot flag alone never grants dashboard access.

The server resolves the mode and passes a boolean to client components. The pilot shell shows leads and email settings, keeps workspace selection/logout/theme, and does not mount inherited billing, upgrade, voice-test, feedback or setup widgets. Creation of a business remains a trusted CLI operation. Email settings hides unrelated tabs; the account-page link is omitted because that page is closed. Shared providers use local locale/cookie preferences and a no-client telemetry context instead of calling closed preference/analytics endpoints. Default component props preserve the legacy behavior in existing tests.

The real HTTP/PostgreSQL test probes all seven methods on `/`, `/leads` and `/settings/email` under anonymous, tenant A, tenant B and forged-header contexts: **21 exact method/path pairs, 84 requests**, plus three fresh-DB access denials and an independent tenant positive control. The root keeps its existing redirect to leads. Configured sessions receive 200 for GET/HEAD on the two dashboard pages, anonymous/forged sessions redirect to login, and unsupported methods receive 405 with an empty body. Every HEAD body is empty. Rendered navigation contains only permitted dashboard links and canonical session identity. Changing verification, active tenant or configuration in the actual database immediately closes page entry; the other configured tenant stays accessible. Both original voice onboarding stages remain unchanged.

The dedicated PostgreSQL access case covers unverified users, foreign active tenants, invalid configuration, paused automation, read-only viewers and revoked membership using actual App/Auth roles with forced role assertions. Six new component cases cover pilot links, disabled billing queries, workspace creation omission, account-menu omission with logout/theme retained, local locale changes and disabled analytics even when cached telemetry preferences exist. The original cases still run.
