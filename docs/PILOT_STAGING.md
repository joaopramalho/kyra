# Email pilot production staging and recovery

Use `docker-compose.pilot.yml --profile prod`, a unique explicit project name and a private copy of `docker/pilot/.env.example`. The inherited Compose remains available unchanged for legacy operation. The pilot file contains only PostgreSQL/pgvector, Redis, migrator, admin and worker. Its migrator applies immutable migrations and bootstraps role passwords before runtime startup; it does not mount the legacy init script that prints generated password-bearing SQL. PostgreSQL/Redis images are pinned by the digests actually pulled locally. Runtime images use the existing pinned Dockerfiles and a reviewed SERVICE_VERSION. Only admin is published, on 127.0.0.1; place an operator-controlled HTTPS reverse proxy in front of it. PostgreSQL, Redis and worker have no published ports. The landing artifact is deployed separately under STATIC_PUBLIC_SITE.md and receives no database/provider credentials.

## Private configuration and manual provider checklist

1. Copy `docker/pilot/.env.example` outside the checkout with mode 0600. Fill every blank and [FILL]. Generate a different 32-byte hex value for each internal secret and database-role password, including the migration, Auth, App, System, Worker and Dispatcher roles. Hex passwords avoid URI interpolation ambiguity. Use a secret manager; do not print the completed file or expanded Compose config into logs. Preserve ENCRYPTION_KEY and signing secrets in the protected disaster-recovery secret store; they are not contained in a database dump.
2. Set APP_BASE_URL and LMC_PUBLIC_BASE_URL to the same HTTPS application origin. Set Google callback exactly to that origin plus `/api/calendar/google/callback`. Create a Web OAuth client, register that URI, configure the consent screen/users and enable the calendar API. Supply its client ID/secret. Actual consent is performed through the existing CLI sequence in TENANT_CONFIGURATION.md; a stored configuration is not evidence of a usable refresh token.
3. Configure the approved sending domain and verified address in Resend. Install the provider-prescribed SPF/DKIM records and the operator's approved DMARC policy; verify them in the provider before sending. Configure an inbound subdomain/MX separately, without replacing an existing business mailbox's MX accidentally. Set LMC_EMAIL_FROM and LMC_RECEIVING_DOMAIN to those real values. Give the Resend API key the permissions needed for sending and retrieving inbound mail, and store the webhook signing secret separately.
4. Register the HTTPS `/api/webhooks/lmc-email` endpoint for email.received, email.bounced and email.complained. The existing adapter verifies the raw signed body and retrieves message content through the receiving API; it requires provider-computed SPF/DKIM/DMARC verdicts and does not trust message-supplied authentication headers. Verify a signed delivery and duplicate/replay behavior with controlled authorized recipients. Missing verdicts remain fail-closed. See [receiving setup](https://resend.com/docs/dashboard/receiving/introduction) and [received email fields](https://resend.com/docs/api-reference/emails/retrieve-received-email).
5. Authentication/verification mail uses the existing SMTP outbox. This profile maps the same Resend key to smtp.resend.com, username resend, port 465 with implicit TLS; see [Resend SMTP](https://resend.com/docs/send-with-smtp). Validate actual signup/verification, password reset and session revocation on the HTTPS staging origin. LMC lead mail uses the existing Resend HTTP adapter. No live-delivery result is implied by offline configuration tests.
6. Supply AI_CHAT_API_KEY and an explicitly approved AI_CHAT_MODEL for the existing OpenAI text-model adapter. Verify structured responses, fallback/handoff and provider failures using controlled leads. No new model recommendation or voice configuration is introduced. Twilio, Polar, Firecrawl, analytics and legacy voice activation are not supplied by this profile; pilot routing remains closed by default and LIVE_PROTOTYPE_ENABLED is false.
7. Use the tenant CLIs to create/configure the verified owner, services/area/hours/FAQ context/escalation/booking rules/calendar and actual footer address. Complete Google consent and availability reconciliation. Confirm A/B isolation, capture, qualified booking, summary, human takeover, follow-up and opt-out under authorized staging recipients. Review legal/contact [FILL] and remove noindex only after the public data is approved.

## Bring up a reviewed deployment

Example shell variables below are paths/names only. Run from the repository root. The preflight validates syntax, strong distinct secrets and origin/callback consistency without echoing values or contacting providers. It does not verify DNS, account permissions or credential validity. Missing real-provider configuration prevents an operational email worker; do not disable its readiness checks.

```sh
PILOT_ENV=/absolute/private/lmc-staging.env
PILOT_PROJECT=lmc-staging
node --env-file="$PILOT_ENV" scripts/pilot-check-env.mjs
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml config --quiet
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml build
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml up -d --wait postgres redis
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml run --rm migrator
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml run --rm migrator node_modules/.bin/tsx dist/cli.js bootstrap
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml run --rm migrator node_modules/.bin/tsx dist/cli.js verify-rls
docker compose --profile prod --project-name "$PILOT_PROJECT" --env-file "$PILOT_ENV" -f docker-compose.pilot.yml up -d --wait admin worker
```

Record the actual image revision, migration journal, independent health/readiness results, HTTPS routing/header checks and provider test outcomes without credentials or lead content. Back up and schedule a maintenance window before applying immutable migrations to an existing deployment. Keep hosted CI, provider acceptance and deployment approvals separate from a local build.

## Backup and deliberate recovery

The existing scripts now accept REPLACEMENT_COMPOSE_FILE; their legacy default is unchanged. Set COMPOSE_PROFILES=prod, REPLACEMENT_COMPOSE_PROJECT to the **reviewed target**, REPLACEMENT_ENV_FILE to its private file and REPLACEMENT_COMPOSE_FILE to the absolute pilot YAML path. Then run `bash scripts/replacement-backup.sh /absolute/new/restricted/backup-directory`. This stops/resumes running admin/worker writers, dumps PostgreSQL and copies local storage with checksums. New backups use umask 077; the copied local-storage tree belongs to the invoking backup operator so that runtime-owned 0600 files can be checksummed without making them public. Restore still assigns runtime ownership to UID/GID 1001. Keep backups private, encrypted off-host and under a measured retention/RPO policy; the Redis queues are reconstructed from durable state and the restore deliberately flushes that deployment's Redis database.

Recovery is destructive to the selected project's database/storage. Quiesce external writers, verify the exact project and backup and retrieve the matching protected encryption/signing secrets. Run `CONFIRM_REPLACEMENT_RESTORE=1 bash scripts/replacement-restore.sh /absolute/reviewed/backup-directory` only with those explicit target variables. Checksums are checked before destructive operations; checksums detect damage, not authenticity. Store/verify backups through an authenticated protected backup system. Verify RLS, roles, worker readiness, calendar reconciliation, outbox/consent/suppression state and controlled delivery before reopening writes. Never use the sandbox test database as a production restore target.

## Isolated rehearsal

Run `bash scripts/pilot-restore-rehearsal.sh` from this checkout with Node, Docker Engine/Compose/Buildx and network access for the first image build. It always allocates a new private temporary directory and fresh lmc-restore-* Compose project on the local default Unix daemon, rejects existing project resources, generates unique local-only database/internal secrets and uses the actual production Dockerfiles. It starts only PostgreSQL/Redis, migrates/bootstrap/verifies the complete schema, invokes the existing PostgreSQL+local-storage marker backup/delete/restore test, verifies RLS again and requires exact name equality with the canonical 88 application tables after marker cleanup, excluding only the same two migration-metadata names as the existing audit and independently requiring preservation of the nonempty migration journal. A damaged dump must be rejected by the real restore command. The owned containers/volumes are removed on exit; mode-restricted backup/evidence files remain for inspection.

No admin/worker consumer is started, no external credentials are needed/generated and no real provider call occurs in this recovery rehearsal. It proves recovery mechanics of the production images/schema/local-storage contract, not live provider connectivity, an HTTPS deployment or a hosted CI run. Inspect its exit status and result.json; a source file or planned command alone is not proof that the rehearsal passed.

For a repeat recovery test against already-built reviewed runtime artifacts, set `PILOT_REHEARSAL_IMAGE_VERSION` to their existing local image version. All three images must exist and carry that exact revision label; there is no fallback pull or rebuild in this mode. The project, data volumes and internal secrets are still fresh and isolated. The original build mode remains the default.
